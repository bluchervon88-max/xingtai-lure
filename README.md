# 邢台路亚 — 安卓钓点记录 App

记录河北省邢台市范围内的路亚钓点与个人作钓流水。**离线优先**：数据全部存本机，
App 本身不申请网络权限，在水库边没信号也能正常记录。

内置 **73 个钓点**（覆盖邢台 19 个区县市），APK 大小 **141 KB**，无任何第三方依赖。

---

## 地图

钓点分布图是**二级页面**（主页顶部一行入口进入），全屏展开、支持双指缩放与拖动平移。

### 底图是自己做的离线矢量图

底图渲染的是**编译进 APK 的真实地理数据**，不是联网地图：

| 图层 | 内容 | 来源 | 体积 |
|------|------|------|------|
| 水系 | 166 个水体轮廓（水库/湖泊/河流面） | OpenStreetMap | 79 KB |
| 区县界 | 604 个环，含邢台 19 个区县 + 周边地市 | OpenStreetMap | 106 KB |
| 河道 | 119 条中心线（沙河、洺河、滏阳河、南水北调干渠…） | OpenStreetMap | 32 KB |

合计 **217 KB**，5.3 万个顶点。数据许可为 ODbL，已在关于页与地图页署名。

### 为什么没有接高德 / 百度的地图 SDK

这是你明确问过的问题，所以把取舍说清楚。三家 SDK 都要求：

1. **申请开发者账号 + 审核 + 包名绑定的 API Key** —— 需要你本人实名申请，我无法代办；
2. **INTERNET 权限** —— 没有它一张瓦片都下载不下来；
3. **联网环境** —— 而水库边经常没信号，恰恰是最需要看地图的时候。

本 App 的定位是「离线优先、不申请网络权限」，接了 SDK 就把这一点推翻了。

**折中方案：要商用地图时用「导航」跳转。** 钓点长按 → 导航到这个钓点，
会把坐标按目标 App 要求的坐标系（高德/腾讯用 GCJ-02，百度用 BD-09）转换后交给对方，
由对方 App 去联网取图。这样你在商用地图上看到的是精确位置，而本 App 依旧零权限。

### 矢量 vs 瓦片

存顶点而不是位图，带来两个好处：

- **放大不糊**：任何缩放级别都是实时投影，不像瓦片放大会看到马赛克；
- **体积小两个数量级**：同样覆盖邢台，瓦片包要 17 MB 起（还只够一个缩放级别）。

### 底图数据的生成与校验

```powershell
# 1) 从 Overpass API 取原始几何（需要联网，只在开发时跑一次）
node tools/fetch-osm-water.js    build/osm-water.json
node tools/fetch-osm-boundary.js build/osm-boundary.json
node tools/fetch-osm-river.js    build/osm-river.json

# 2) 简化 + 量化 + 压缩成顶点流
node tools/build-basemap.js build/osm-water.json    assets/basemap_water.txt    water
node tools/build-basemap.js build/osm-boundary.json assets/basemap_boundary.txt boundary
node tools/build-basemap.js build/osm-river.json    assets/basemap_river.txt    river

# 3) 校验编解码一致（自己写的格式，必须验）
node tools/verify-codec.js
```

**顶点编码格式**（`tools/basemap-codec.js` 与 `Basemap.java` 必须严格对应）：

```
行格式:  类型|顶点流|local|标注y|标注x|名称
类型:    W 水体面 / B 区县界 / R 河道线

顶点流:  点数 + 各点增量，base-32 + 续位标记
         · 每位 5 位数 -> 字符 (char)('0' + d)，即 '0'~'O'
         · 除最后一位外，字符码 +0x20，得到 'P'~'o'
         · 解码时看字符码是否 >= 0x50 判断"后面还有"
         · 值映射：非负 v -> 2v，负数 v -> 2|v|+1
```

这里踩过两个坑，都记在代码注释里了：

- **一开始想用 36 进制变长整数，但解码端无法定界** —— 没有分隔符时，
  读到一个字符无法判断它是"独立的一个数"还是"更长的数的一部分"。
  改成续位标记后才有明确的边界。
- **符号映射写反过**：编码用 `2|v|+1`，解码却写成 `-(value+1)/2`，
  差一位导致所有负值都错 1。`verify-codec.js` 的往返测试立刻抓了出来 ——
  自定义二进制格式一定要有这层校验，否则地图会画出乱七八糟的形状且极难定位。

### 主页：一整块连续滚动

主页只有**一个滚动体系**，从上到下依次是：分布图入口 → 结果计数 → 钓点卡片列表。
三者同属一个滚动容器，手指一划整体移动，不存在"上半一块、下半一块"的拼接感。

地图**不在主页**。它占高度大，放在主页会把列表挤成一条；作为"看整体分布"的工具，
它更适合独立页面。主页专注"找具体钓点"，地图在二级页面全屏展开（支持双指缩放、拖动平移）。

### 钓点列表不用 ListView

列表用 `SpotListView` + `SpotCard`，**一次性构建全部卡片，不做视图回收**。

原因：`ListView` 靠"回收 + 重新绑定"复用行视图，只要有一条属性忘了重置，
就会把上一个钓点的内容残留在新行上——真机上表现为"同一个位置显示了两个不同的钓点"，
而且时好时坏、极难复现。整个项目被这个问题坑过两次。

本 App 只有几十条钓点，一次性构建的代价很小（每张卡 8 个 `TextView`，73 张约 600 个视图），
换来的是**结果完全确定**：不存在回收，也就不可能存在残留。
如果将来数据涨到几百条以上，应改用 `RecyclerView` 并严格实现 `onViewRecycled`。

### 尺寸不写死 dp，走 ScreenFit 推导

`src/com/xtlure/app/util/ScreenFit.java` 是屏幕适配层，核心思路是**先量再算**：

```java
ScreenFit.get().init(this);                    // onCreate 最先调用，采集物理屏参数
ScreenFit.get().refreshUsable(contentRoot);    // 布局完成后用实测位置校正可用高度
int tabBar = ScreenFit.get().tabBar();         // 弹性尺寸，自动夹紧到合理区间
int touch  = ScreenFit.get().touchMin();       // 48dp 触摸下限
```

为什么必须要有这一层：这台测试机（vivo V2505A）上出现了两个反直觉的情况——
系统设置了 density override（实测 600dpi），并且**应用窗口高度 3168px 比屏幕可用高度
3026px 多出 142px**。所有写死的 dp 尺寸都因此算错，症状是"设了 64dp 实际只有 39dp、
标签栏只剩一条边"。

适配层的做法是不相信任何窗口声明的高度，直接看内容视图**实际落在屏幕的哪一段**，
再用可用高度去推导标签栏、间距、奖章直径等尺寸（`flex(设计值, 下限, 上限)`）。

配套还有一道兜底：`ensureContentFitsScreen()` 在每次布局后比对根视图底边与屏幕高度，
超出就补差额的内边距，把内容顶回可见区域。

## ⚠️ 先说一句实话：邢台路亚资源偏弱

做完两轮调研后必须诚实告诉你这件事，因为它会改变你该怎么用这个 App。

**"能钓"不等于"有鱼"。** 真正找到路亚钓获硬证据的只有三处：

| 水域 | 证据 |
|------|------|
| **朱庄水库** | 钓获贴明确写"路亚喜中小翘嘴"；本地钓友回复"让钓啊！偶尔收费，去年是一位二十" |
| **七里河市区段** | 钓友点名"七里河就能玩"；2025 年 10 月市交建文旅集团还主办了官方路亚船钓公开赛 |
| **沙河（南阳河）** | "一下午路亚钓了 7 条马口" |

而被广泛点名的六座水库——临城水库（岐山湖）、野沟门、东石岭/秦王湖、马河（鹊山湖）、
乱木、八一（羊卧湾）——**搜遍中文互联网找不到一条路亚钓获记录**，鱼种结构以放养鲤鲫为主，
是传统台钓场。去钓鱼吧网站的"邢台路亚"钓场类目**全境 0 条收录**，侧面印证了这一点。

**所以这个 App 的定位应该是：合规提醒 + 记录工具 + 微物路亚（马口/白条）**，
而不是"翘嘴鲈鱼大物库"。它的核心价值在于**帮你把标点和规律记下来，越用越准**——
本地没有现成的路亚资源清单，你的记录就是最稀缺的那份数据。

另外三条会直接影响你出门的发现，已写进数据：

- **野沟门水库 2024 年起腾库施工，基本无水**，现在去大概率空军
- **乱木水库存在冲突**：2022 年有"收费 50 元/12 小时"实拍，但 2025 年市水务局
  防溺水通告点名乱木水库"禁止垂钓"。下竿前务必电话核实（临城 0319-7192081）
- **园博园（襄湖）、达活泉公园禁钓；狗头泉/百泉高概率禁钓；南水北调干渠绝对禁钓**

## 改版本号

版本号的**唯一来源是 `AndroidManifest.xml`**：

```xml
android:versionCode="2"      <!-- 整数，每次发版必须递增，Android 用它判断升级 -->
android:versionName="1.1"    <!-- 给人看的 -->
```

改完直接构建即可。`build.ps1` 会读这两个值、传给 aapt2，
**构建完还会用 `aapt2 dump badging` 从 APK 里读回来比对**，不一致就直接构建失败；
`versionCode` 不是整数也会被拦下。关于页的版本号从 `PackageManager` 读取，
永远显示已安装 APK 的真实版本。

以前版本号在 manifest 和 build.ps1 里各写一份，结果改了一处、装出来还是旧版本号 ——
现在结构上不可能再发生。

## 关于 `.idsig` 文件（已不再生成）

早期构建时 `dist/` 里除了 APK 还有一个 `XingtaiLure-debug.apk.idsig`。说明一下它是什么：

- 它是 **APK Signature Scheme v4 的签名文件**，由 `apksigner` 生成。
- **v4 签名不写进 APK 内部**，而是这个独立的旁挂文件。可以用 `apksigner verify --verbose`
  看到区别：v1/v2/v3 显示 `true`（在包内），v4 显示 `false`（在包外）。
- 它的唯一用途是 `adb install --incremental`——把 APK 按块流式传给设备，
  设备边收边校验，只传输实际需要的部分，适合几十 MB 的大包。
- **正常安装、直接拷贝 APK 到手机、各种应用市场都不需要它。**
  它也不需要跟着 APK 一起分发，单独留着没意义，删掉不影响任何安装方式。

我们 129 KB 的包用不上增量安装，所以构建脚本已显式加 `--v4-signing-enabled false` 关掉它。
签名方案保留 v1（兜 Android 6 及以下）+ v2（兜 Android 7 及以上），
构建末尾会自动校验这两个方案确实在包内，缺任何一个都直接构建失败。

### 怎么查手机上的数据库

正式包**不含** `android:debuggable`（生产包不该开）。需要查库时用诊断模式构建：

```powershell
# 生成带 debuggable 的临时包到 dist/diagnostic.apk（不会修改 AndroidManifest.xml）
powershell -ExecutionPolicy Bypass -File build.ps1 -Diagnostic
& 'C:\dev\android\sdk\platform-tools\adb.exe' install -r dist\diagnostic.apk

# 查库（设备自带 /system/bin/sqlite3）
$adb = 'C:\dev\android\sdk\platform-tools\adb.exe'
& $adb shell "run-as com.xtlure.app sqlite3 databases/xtlure.db 'SELECT seed_version, COUNT(*) FROM spot GROUP BY seed_version;'"

# 查含中文的 SQL 要写成 UTF-8 文件再执行，避免 shell 吃掉引号与中文
# （用 Out-File -Encoding ASCII 会把中文变成 ?，必须用 UTF8Encoding($false)）
& $adb push q.sql /data/local/tmp/q.sql
& $adb shell "run-as com.xtlure.app sh -c 'sqlite3 databases/xtlure.db < /data/local/tmp/q.sql'"
```

诊断模式只在构建过程中对 manifest 的**临时副本**注入 debuggable，源文件始终干净，
构建结束副本即丢弃，所以正式包不会受影响。

### 崩溃与布局诊断

部分国产 ROM（实测 vivo）会把应用 logcat 整个过滤掉，crash 缓冲区也查不到。
因此 App 内置了不依赖 logcat 的记录机制：

- 未捕获异常 → 写入 `Download/xtlure-crash.txt`（adb 可直接读，无需 debuggable）
- 同时写一份到应用私有目录 `files/crash.txt`
- 启动流程打点（仅调试构建）与**布局缺陷自检**（始终生效，只在异常时写文件）

布局自检会检查标签栏高度、内容区高度、顶栏占屏比例、标签栏是否超出屏幕下沿，
一旦命中就写入 crash 文件 —— 这类缺陷在正式包里同样致命，所以不限于调试构建。

  顺水河、留垒河，以及西部山区四道大川（路罗川、浆水川、将军墓川、宋家庄川）
- **湖泊 5 处**：南宫湖、邢州湖（大陆泽湿地）、百泉狗头泉、达活泉公园、园博园
- **渠道 1 条**：南水北调中线干渠
- **收费钓场 23 家**：带实测坐标

### 坐标精度必须说清楚

| 可信度 | 含义 | 条数 |
|--------|------|------|
| `web` 网络资料 | 公开钓点库的实测坐标，误差几十米 | 26 |
| `unverified` 未核实 | 按公开地理资料与行政区位置估算，**误差可能到公里级** | 47 |

**那 47 条未核实的坐标只能用来在地图上找到大致方位。** 文献里查不到精确点位，
我不愿意编造 6 位小数的假坐标——那在野外比没有坐标更害你。正确用法是：
到了水边点详情页的「取坐标」用手机 GPS 校正一次，再把可信度改成「本人实地确认」。

### 禁渔期：这是 App 里最重要的合规信息

依据邢台市及各区县农业农村局通告原文：

- **禁渔期**：5 月 16 日 12 时 — 7 月 31 日 12 时（河北省海河流域，邢台全市）
- **禁止作业类型（通告原文）**：「除钓具之外的所有作业方式」
  → **钓具垂钓本身被豁免**
- **严打对象**：「以休闲垂钓为幌子的一人多杆、多钩线钓、锚鱼」
- **一处订正**：网上流传的「一人一杆一线一钩」**没有找到河北省或邢台市的官方条文出处**。
  App 里已改为**原样引用通告措辞**，并明确标注这一条查不到出处 —— 不把流传说法当法规用。
- **路亚的实际风险**：路亚竿属钓具、文本上被豁免，但**三本钩硬饵在禁渔期内有被按
  「多钩线钓」认定的风险**（推断，未核实）。稳妥做法是禁渔期内改用单钩软虫或亮片。
- **刑事红线**：2022 年南和区有人用撒网捕 4 条白鲢，被以《刑法》第 340 条
  非法捕捞水产品罪处理。禁渔期内用网具是刑事风险，不是罚款问题。

App 的处理方式：

- 首页顶部有禁渔期状态徽标，进入禁渔期时显示醒目横幅（含通告原文措辞），非禁渔期则显示倒计时
- 每个天然水域钓点的详情页有独立的禁渔期卡片 + 通告原文 + 路亚三本钩风险提示
- 收费黑坑/养殖塘自动标注"不受禁渔期约束"
- 「我的 → 合规须知」列出来自 8 个区县通告的合规要点，**含各县举报电话**
- 列表卡片上处于禁渔期的钓点会显示 ⛔ 提示

### 预置数据的更新机制（重要）

预置数据带版本号（`Seed.java` 的 `SEED_VERSION`）。App 启动时会：

| 情况 | 行为 |
|------|------|
| 新钓点 | 插入 |
| 已有钓点，且是旧版预置数据 | **刷新坐标与资料**（本轮 4 处坐标修正就是这样到达你手机的） |
| 已有钓点，且你标记过「本人实地确认」 | **绝不覆盖**，只记下版本号 |

最后一条是关键：**你自己用 GPS 核实过的数据，比任何公开资料都准，永远不会被覆盖。**
所以到了水边点一下「取坐标」再改可信度，这个钓点就真正锁定了。

你自己添加的钓点（不来自预置数据）也不在任何刷新范围内。

| 页面 | 内容 |
|------|------|
| **钓点** | **钓点分布图**（纯 Canvas 绘制散点图，可折叠，点圆点直达详情）；卡片列表（类型图标 / 区县 / 状态 / 距离 / 对象鱼 / 最近记录）；搜索、按区县筛选、**按水域类型筛选**、只看收藏、按名称或距离排序 |
| **钓点详情** | **禁渔期卡片**；导航 / 复制坐标 / 记一次 / 编辑 / GPS 补录坐标；三种坐标系并列；今日日出日落与黄金窗口；历史作钓记录 |
| **记录** | 作钓流水卡片（鱼种、尾数、用饵、钓法、天气气压水温）；新建与编辑表单，常用值一键点选 |
| **我的** | 数据统计；**成就徽章**（带进度）；**作钓洞察**（最出鱼的拟饵/钓点/月份、气压与鱼口关系）；配色主题切换；导出 JSON 备份与 Markdown 清单、从备份恢复、清空数据；地图偏好 |

### 作钓洞察 —— 数据攒起来才有价值

「我的」页会从你的记录里自动算出：

- **最出鱼的拟饵**：累计尾数、用了几次、平均每次几尾
- **最出鱼的钓点**：去过几次、累计几尾
- **最常钓到的鱼**
- **你的高产地月份**
- **气压与鱼口的关系**：把气压 <1005 和 ≥1015 的记录分组对比平均尾数。
  只有在两边都至少 2 个样本时才给结论，并明确标注"样本少时结论不可靠"

最后这条是这个 App 最独特的地方——它只存在于你自己的记录里，任何现成的钓鱼 App
都给不了你，因为它需要**你**在同一片水域反复出钓并记录气压。

### 钓点分布图

不引入任何地图 SDK（那需要申请 key、有瓦片版权与配额问题，还会破坏"不申请网络权限"），
而是用等距圆柱投影把经纬度直接画成散点：

- 圆点按水域类型着色，收藏的点加金色圆环，禁渔点标红
- 蓝圈是"我"的当前位置
- 标注经纬度范围与正北方向
- 点任意圆点直接进详情

不追求地理精度，只用于看清"西部山区水库多、东部平原河道多、市区南边黑坑密集"这类规律。

### 三套配色与主题

「我的 → 外观 → 配色主题」可在两套配色间切换，切换后毫秒级重建界面：

| 主题 | 底色 | 主色 | 适用 |
|------|------|------|------|
| **夜钓（深色）** 默认 | `#0E1116` | `#2FB6A8` 水青 | 晨昏与夜间出钓不刺眼 |
| **日间（浅色）** | `#F2F4F7` | `#12897D` 深青 | 白天强光下更清楚 |

两套配色的对比度都由 `tools/ThemeTest.java` 用 WCAG 公式审计过
（正文 ≥ 4.5、次要文字 ≥ 3.0、状态色 ≥ 3.0）。加这个测试是有原因的：
浅色主题的收藏星最初用了 `#D99A00`，对比度只有 2.45，太阳底下根本看不见 ——
这是肉眼审不出来、但脚本一算就露的问题。

### 三个值得说明的设计

**1. 坐标统一只存 WGS-84。**
数据库里永远是 GPS 原始坐标，展示/导航时才实时换算。高德腾讯用 GCJ-02、
百度用 BD-09、与 WGS-84 相差 300~600 米 —— 不换算在野外等于找不到钓点。
点「复制坐标」会一次性给出三种坐标系加一条高德链接。

**2. 资料可信度分级。**
每个钓点带 `未核实 / 网络资料 / 本人实地确认` 标记。预置数据全部是**未核实**，
坐标是按公开地理资料估算的，只能用于在地图上找到大致方位。到现场用
「取坐标」按钮用 GPS 校正一次，再改可信度，这个钓点就真正属于你了。

**3. 明确标出不能钓的地方。**
南水北调干渠、市区公园水域等被标为「禁钓」并给出原因。知道哪里不能下竿，
和知道哪里能下竿一样重要。

**4. 气压手填，而不是联网取。**
路亚很吃气压，但加压天气接口基本都要申请 key，而本 App 刻意不申请网络权限。
所以气压做成快捷项：手机上任何天气 App 都能看到气压值，记渔获时顺手填一下。
几次之后你就能看出同一个钓点气压 1020 和 995 的鱼口差别 ——
这是别人给不了你的数据，因为它只存在于你自己的记录里。

    ...

private static Ui buildLight() { ... }   // 日间（浅色）
```

改这里 = 换肤。想加第三套主题，复制一个 build 方法、在 `applyFromPrefs` 里加分支即可。

### 2. `src/com/xtlure/app/util/Ui.java` —— 尺寸与通用积木

public static final int RADIUS_CARD = 14;  // 卡片圆角
public static final int GAP_M       = 12;  // 标准间距
public static final int TEXT_TITLE  = 17;  // 标题字号
```

另外 `Ui.chip() / Ui.kv() / Ui.card() / Ui.section()` 是所有页面的通用积木，
改一个所有页面一起变。

### 3. 各页面的排版代码

| 想改什么 | 改哪里 |
|---------|--------|
| 顶部栏（标题 + 统计 + 日出日落） | `MainActivity.refreshHeader()` |
| 底部标签栏 | `MainActivity.buildTabBar()` |
| 钓点卡片长什么样 | `SpotAdapter.build()` / `bind()` |
| 记录卡片长什么样 | `CatchAdapter.build()` / `bind()` |
| 钓点详情页版面 | `SpotDetailActivity.render()` |
| 新建/编辑钓点表单 | `EditSpotActivity.onCreate()` |
| 记一次作钓表单 | `CatchDialog.onCreateDialog()` |
| 空状态文案 | 各 Fragment 的 `reload()` |

全部用代码构建布局（没有 XML 布局文件），这是刻意的选择：改版时只动一个
Java 文件，不用在 XML 和 Java 之间来回对。想换成 XML 也可以，把对应
`build()` 方法换成 `inflater.inflate()` 即可。

`ThemeTest` 会用 WCAG 对比度公式检查两套配色是否都还看得清，

## 加钓点：两种方式

### 方式一：直接在手机上录（推荐）

钓点页 → 右下角 `＋` → 填名称 → 点「用 GPS 取当前坐标」→ 保存。30 秒搞定。
内置的 73 个钓点不用你逐个录入，但**你自己发现的标点**（某个闸口、某段回水湾）
才是最值钱的，录进去就永远是你的。

### 方式二：批量改预置数据

编辑 `assets/spots_seed.json`，然后**把 `Seed.java` 里的 `SEED_VERSION` 加 1**，
不然 App 不会重新导入。字段格式：

```json
{
  "name": "朱庄水库·主坝区",
  "lat": 37.0315, "lon": 114.1657,
  "waterType": "水库",
  "status": "限钓",
  "district": "沙河市",
  "address": "沙河市西部山区，澧河（大沙河）上游",
  "fish": ["翘嘴", "鲈鱼", "马口"],
  "lure": ["亮片", "米诺", "VIB"],
  "bestSeason": "4-6月、9-11月",
  "access": "自驾到坝顶附近",
  "note": "开阔水面，清晨翘嘴追饵",
  "risk": "⚠ 是否允许垂钓以现场规定为准",
  "closedSeason": "信都区通告：5月16日12时—7月31日12时属休禁渔区",
  "confidence": "web",
  "source": "https://zainadiao.com/reach/HYDA.0e9a55f754bc/"
}
```

- `waterType`：水库 / 河流 / 湖泊 / 池塘 / 黑坑 / 渠道 / 沙坑 / 未分类
- `status`：可钓 / 禁钓 / 收费 / 限钓 / 待确认
- `confidence`：`unverified`（估算）/ `web`（有公开来源的实测坐标）/ `field`（本人实地确认）
- `lat`/`lon` 必须是 **WGS-84**（手机 GPS 原始值，即高德坐标往西南偏 300~600 米）
- `closedSeason` 不填会用文件级的 `closedSeasonDefault` 兜底

改完跑一次校验：
```powershell
node tools/validate-seed.js assets/spots_seed.json
```

## 技术选择说明

**为什么不用 Gradle？**
这台机器没有 Android Studio、没有 Gradle、没有 Maven 依赖解析能力。
`build.ps1` 只用 Android SDK 自带的命令行工具：

```
aapt2 compile  资源 -> 扁平中间产物
aapt2 link     生成 base APK + R.java
javac          编译 Java（只对 android.jar）
jar + d8       class -> classes.dex
jar uf         把 dex 塞进 APK
zipalign       4 字节对齐
apksigner      签名
```

**为什么没有任何第三方库？**
因为上面这条流水线解析不了 Maven 依赖。所以 `Json.java` 是自己写的 200 行
解析器，`SimplePager.java` 是自己写的 40 行三页容器（替代 ViewPager），
UI 全部用系统 framework 的 View 代码构建。代价是少了一些现成组件，
好处是 APK 只有 88 KB、启动快、永远不用担心依赖漏洞。

**坐标系转换和日出日落为什么自己实现？**
同样是因为不能引依赖。这些是纯数学，实现了就能离线跑，
而且能写测试验证精度（见 `CoreTest`：邢台夏至日出 05:02、冬至 07:32，
正午太阳高度角夏至 75.4° / 冬至 29.3°，均与公开天文数据吻合）。

## 已知限制

- **预置坐标是估算值**，city 级精度，必须现场用 GPS 校正。这是数据来源本身的
  限制，不是 bug。
- **没有内置地图**。地图要装高德/百度/腾讯任一，或退化成网页地图。这样做避免
  了地图 SDK 的 key 申请和内嵌瓦片版权问题，也保住了"不申请网络权限"。
- **天气与气压靠手填**（见上文设计说明 4），不是自动获取。这是"离线优先"的
  必然代价。
- **仅 arm 通用**。纯 Java 无 native 库，所以任何 CPU 架构的安卓机都能装。
- 最低支持 **Android 5.0（API 21）**，目标 API 34。
